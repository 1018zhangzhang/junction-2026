## 1. 这是什么

把一份菜谱拆成「一步一屏」摊在抬头视野里，并且**不碰手**：

- **一屏看全**：11 道家常菜分两列摆在画面里（左列 1-6、右列 7-11），不翻页、不滚动；两列关于画面中线对称，列内居中；
- **说就选**：说编号（`3` / `三`）或菜名（`番茄炒蛋`，只说 `番茄` 也认）；选中的那道放大到 31 号、提到近白、浮到画面中间，其余淡出 —— 0.9 秒过场，看得见"我选的是它"；
- **说就动**：`下一步` / `上一步` / `跳过` / `停` / `继续`，全程不用按键；
- **说就问**：`太咸了` `火太大` `两个人吃` `加两勺生抽` —— 答案出在步骤下方，主步骤不乱跳；
- **忌口一句话**：`不吃辣` → 辣菜变暗标「辣」，推荐也避开它（这一版记到本次运行结束，重启要重说）；
- **不认识的菜直说**：说一道菜单里没有的菜，就提示从菜单里选，不联网瞎编；
- **做完会收尾**：`完成了` → 问「要存进菜单吗」→ 问「还做下一道吗」→ 收工总页（今天做了几道、各用多久）。

菜单内置 11 道家常菜。做完说「加进去」的菜会存到应用数据目录，下次排在菜单最前面。

> **文档状态（2026-11-08 · v58c）**：当前代码是**能跑通的那一版**（v58 基线，只加了菜单居中美化与两处语音参数修正）。
> 下面 §9 之后是历次迭代的过程记录 —— 其中 **v65 开机点阵、v66 滚动菜单、v67 字号舒适档、v68 忌口记忆、v81/v82 的修法都不在这一版里**，
> 依赖它们的 `src/boot-anim.js`、`src/taste.js`、墨色阶梯模块也已随回退删除，对应的三套测试一并移除。
> 要取回任意一版：`git checkout cook-v68`（tag 都在）。

## 2. 60 秒演示脚本

| # | 你说 / 你打 | 屏幕上应该发生什么 |
|---|---|---|
| 0 | `开始` | 冷启动是点阵动画（21×9 个方块，气泡从底部往上浮）；说「开始」→ 进菜单（8 道一屏，右侧 `约 N 分`）|
| 0.5 | `下一条` | 光标往下挪一道，窗口跟着滚；黄字行显示「当前 N. 菜名 · 约 M 分」|
| 1 | `番茄炒蛋` | 状态点 `[待命]` → `[处理中]` → `[跟做]`，第 1 步出现 |
| 2 | `大字` | 主步骤 30→38 号字（状态点仍是 `[跟做]`，右上角 `输入 · 语音/文本`） |
| 3 | `精简` | 只剩「第几步 / 主步骤 / 倒计时」，字幕与底栏撤掉 |
| 4 | `恢复` | 回到常规布局 |
| 4.5 | `看不清` | 底栏/麦克风行/状态徽章从 14 号抬到 16 号（主步骤、菜名不动）；说 `字小一点` 还原 |
| 5 | `太咸了` | 主步骤不动，下面出一行补救建议（留 10 分钟，直到下一次回答） |
| 6 | `下一步` | 第 2 步；上一步的建议还在（不冒充新内容：它挂在原来那一步上） |
| 7 | `完成了` | 状态 `[待确认]`（问存不存）→ `不用` → `[完成]` 收工总页 |

## 3. 运行

### 3.1 环境

| 项 | 版本 |
|---|---|
| 宿主 | Ubuntu 22.04（WSL2 可用，需配好音频） |
| Node.js | **24.13.0**（kit 精确校验，高/低都会拒绝） |
| npm | 11.6.2 |
| 第三方依赖 | **0 个**（`package.json` 的 dependencies 为空） |

```bash
export KIT="$HOME/IrisView/LLVISION/IrisView-Developer-Kit-v1.0.0"
cd cook-frame
"$KIT/bin/irisview" test .                      # 清单 + 依赖 + 语法
bash tools/pack.sh                              # test → build → package 一条龙
bash tools/pack.sh --run                        # 打完直接进模拟器
```

> 只 `build` 不 `package`，模拟器跑的还是旧包。`tools/pack.sh` 里已经按顺序串好。

### 3.2 两条路径（重要）

| 路径 | 需要什么 | 能演示什么 |
|---|---|---|
| **A. 零配置（评委默认）** | 什么都不配 | 文字输入全套功能：选菜、翻步、改量、布局、收尾；**8 项验收用例全部可跑** |
| **B. 配密钥（完整）** | 一个 `llm.json` + 本机 `asr_server.py` | 加上语音输入、豆包同源整句识别、现场生成菜谱、联网问答 |

语音链路依赖外部服务，**没有密钥时语音会明确报错、文字照常可用**（状态点会亮 `[异常]`，底栏写"识别服务没连上"）—— 这是设计好的降级，不是崩溃。

### 3.3 配模型 / 配语音

把 `llm.example.json` 复制成 `llm.json`，放到**应用数据目录**（启动日志 `COOK_LLM ready …` 那行会打出路径；环境变量是 `FUSIONUI_APP_DATA_DIR`），不要放进 `src/`，也不要提交。

- 脑子：任何 OpenAI 兼容 `/v1/chat/completions`（当前用硅基流动 `Qwen3-8B`，`enableThinking:false`）
- 耳朵：`asr.final` 支持数组，按顺序试。当前配置：① 火山「流式语音识别 2.0」一句话识别（`volc-sauc`，中文准确率最高）② 硅基 SenseVoice（兜底）
- 本地流式字幕：`http://127.0.0.1:5001/asr`（`asr-service/asr_server.py`，Vosk）

账号申请：火山引擎控制台 → 语音识别 → 开通「流式语音识别 2.0」（送 20 小时）→ API Key 管理复制唯一 Key；硅基流动 → API 密钥。**两处都是用自己的账号，仓库里没有任何密钥。**

## 5. 架构

```
src/index.js      界面与交互总控：窗口、每帧绘制、状态徽章、布局档位、滚动菜单、输入轮询
src/voice.js      麦克风会话 + 流式字幕 + 静音判句（平台 input API）
src/asr.js        整句识别编排：豆包 sauc → 火山 flash → SenseVoice → 本地，逐级降级
src/asr-volc-ws.js 火山 v3 二进制协议（手写 TLS 握手 + WebSocket 帧）
src/engine.js     纯逻辑状态机：一句话 → 意图 → 新状态 + 该显示什么（无 UI 依赖）
src/wrap.js       收尾两问：要存吗 / 还做吗 / 收工（否定优先）
src/llm-bridge.js OpenAI 兼容客户端：生成菜谱 / 听错纠正 / 一句话问答
src/agent.js      联网问答（可选）
src/recipe.js     11 道内置菜谱 + 启动时合并收藏菜
src/dish-store.js 收藏落盘（原子写、同名覆盖、上限 6）
src/boot-anim.js  开机点阵动画：189 个 Board 方块 + 气泡上浮（纯函数可单测）
```

设计原则：**判断逻辑不碰界面**。`engine.js` / `wrap.js` 都能用纯 Node 跑测试，界面挂了不影响逻辑，逻辑错了不用开模拟器就能定位。

## 7. 已知边界（如实说明）

1. **语音依赖外部服务**：没有 `asr_server.py` 或没有火山/硅基密钥时，语音不可用，文字通道完整可用。
2. **生成一道新菜要 5~15 秒**（先纠正再生成，两次模型调用），期间状态点是 `[处理中]`；不做流式打字机效果。
3. **长句会被平台切成两段**：已有 900ms 同文去重，但用户连说两遍同一句只会执行一次。
4. **菜单是滚动列表**：一屏 8 道；编号是绝对编号（第 9 道就是 9，跟窗口位置无关）。说「下一条」挪一格、「下一页」挪一屏；光标那道提亮，黄字行同步显示「当前 N. 菜名 · 约 M 分」。
5. **收尾只问"库外菜"要不要存**：内置菜不重复问。
6. **对话行的答案按"问它的那一步"保留 10 分钟**，换步不撤（用户明确要求），但不会被当成新步骤的内容。

## 10.（历史）v64 新增细节：文本不裁字 + 步骤进度

### 10.1 文本不再被硬裁（`fitText`）

平台 Text 控件不会自动缩字号，字超出框就被切掉半个。现在所有会变长的文字都先按「每行几个字 × 能放几行」截断并补 `…`：

| 控件 | 位置 / 尺寸 | 字号 | 约可容纳 | 说明 |
|---|---|---|---|---|
| 主步骤 `main` | y120~320（随布局变） | 30 / 32 / 34 / 38 | 80 字 | 「大字/重点/精简」换布局时阈值跟着变 |
| 对话行 `sub` | y330~390，640×60 | 16 | 约 78 字 | 答案 + 「第 N 步 ·」前缀一起算 |
| 字幕行 `partial` | x12、360×26 | 15 | 约 23 字 | 只能一行，超了截断 |
| 顶部进度 `progress` | y26~56，640×30 | 14 | 约 45 字 | 菜单/跟做/收尾通用 |
| 黄字行 `timer` | y64~98，640×34 | 20 | 约 32 字 | 倒计时 / 提示 |
| 底栏 `footer` | y448~472，640×24 | 12 | 约 53 字 | 菜单/跟做/收尾各有文案 |
| 菜单行 / 收工列表 | 列宽 × 28 | 19 | 按列宽算 | 长菜名带「（新）」「（辣）」也不会压到右列 |

判据写在 `test-menu-list.js`：短文一个字都不许动；同一个 21 字句子在 200 高的跟做页能放两行，在 36 高的菜单标题区必须截断。

### 10.2 步骤进度条 + 剩余时间

- **进度条**：12,57 起、616×5 的一条细长条，用 `Board` 画（不依赖字体里有没有方块符号），填充比例 = (当前步 + 1) / 总步数；菜单页和收尾页整条收起，不留黑杠。
- **剩余时间**：顶部进度行变成「第 3 步 / 共 7 步 · 还剩约 6 分 · v64」。按当前步及之后所有 `timeMs` 求和；一旦说了「开始计时」，当前步换成计时器的实时剩余量，倒计时走字时这个数字也会跟着减。
- **可核对证据**：日志 `COOK_BAR 25% w=154`（比例 + 像素宽）、`COOK_PAINT … progress="第 1 步 / 共 4 步 · 还剩约 19 分 · v64"`。

## 11.（历史）v65 新增：开机点阵 + 「开始」闸门

### 11.1 为什么要这一屏

以前一启动就是 12 行菜名 —— 评委第一眼看到的是"已经选好了"，整段演示缺一个起点，也缺一次「待命」状态的可见证据。现在冷启动先演点阵，说一句「开始」才进菜单。

### 11.2 点阵怎么画的

- **不用字符画**：眼镜字体里通常没有 `█ ░ ●` 这类方块字符（会渲染成豆腐块），所以用 **189 个 `Board`**（21 列 × 9 行、每点 10×10、间距 20）真实方块拼成点阵，颜色可以逐点改。
- **位置**：`x=115~525`、`y=110~280`，正好落在主标题区（120~320），上面给「开机 · v65」一行，下面 330 给提问行，互不重叠。
- **动画**：底部先"灌水"逐行亮起（前 750ms），之后每列两颗气泡从底部往上浮、越往上越淡 —— 像锅里在咕嘟，和"做饭助手"是一回事。
- **性能**：亮度量化成 6 档，每帧只改"档位真的变了"的点。实测稳定态一帧改 20~100 个点（不是 189 个），80ms 一拍；进菜单立刻停表。

### 11.3 闸门怎么开（三个边界）

| 情况 | 行为 |
|---|---|
| 说 `开始` / `开始吧` / `走起` / `开工` / `你好` / `hello` | 进菜单（日志 `COOK_BOOT_START via=start-word`） |
| 直接说菜名（≥2 字，如 `番茄炒蛋`） | 放行：进菜单并直接开做那道菜（`via=dish`） |
| 说别的（`今天天气不错`） | 停在点阵页，提问行回显「听到「…」· 说「开始」进菜单」 |
| 没麦克风 | 键盘打 `开始` 一样进；按确认键也算 |
| 60 秒没人理 | 自动进菜单（`via=timeout`），避免看起来卡在开机画面 |

进菜单前一定会把 189 个方块收成 0 尺寸（日志 `COOK_BOOT_DOT hide`），否则会压在菜名列表上。

### 11.4 可核对证据

```
COOK_BOOT_DOT start grid=21x9
COOK_BOOT_ANIM f=1 t=99ms changed=29        ← 点阵真的在刷（每 0.8 秒一条）
COOK_BOOT_ANIM f=11 t=891ms changed=104
COOK_BOOT_DOT hide                          ← 进菜单前收干净
COOK_BOOT_START via=start-word
```

`node tools/test-boot.js`：20 项（尺寸不出画布、亮度 0~1、底行先亮、相邻帧有变化、`apply` 只改变化点、`hide` 收 189 个点、没有 `Board` 时返回 null 不抛）。`node tools/mock-boot.js`：新增「开机点阵」组，验证"乱说不理 / 说开始进菜单 / 进菜单后定时器已停"。

## 12.（历史）v66 新增：滚动菜单 + 预计时间

### 12.1 为什么从"分页"改成"滚动"

原来一屏 12 道、两列排满，多了就分页。两个实际问题：

1. 一页只有 12 个坑，收藏 6 道 + 现场生成几道就要翻页，翻页后用户容易记错"第 13 道到底在第几页"；
2. 两列排布挤不下"这道菜要多久"这一列 —— 而做饭的人最先想知道的就是这个。

现在改成**单列纵向滚动**：一屏 8 道（`LIST_ROWS = 8`），右侧一列预计时间，光标上下挪、窗口跟着滚，菜再多也只是多滚几下。

### 12.2 版面（都是 1:1 真实坐标）

| 元素 | 位置 | 说明 |
|---|---|---|
| 菜名列 | `x=24 ~ 492`，19 号字 | `1. 番茄炒蛋`，AI 生成的带「（新）」 |
| 时间列 | `x=500 ~ 616`，15 号字、右对齐 | `约 8 分`，暗绿一档，不抢菜名 |
| 行距 | `LIST_H = 30 × FONT_SCALE` | 8 行到 398，麦克风行 404 之前收住 |
| 黄字行 | `y=64` | `当前 3. 拍黄瓜 · 约 10 分`（光标 + 时间，滚动时同步变） |
| 顶部进度 | `y=26` | `菜单 · 共 11 道 · 第 1-8 道 · v66` |

时间口径：优先用菜谱的 `totalMs`（含准备/等待的总时长），没有就按步骤 `timeMs` 求和；不足 1 分钟按 1 分算，**90 分以上才换算小时**（`约 1.5 时`），60~89 分仍写 `约 65 分`（比"1.1 时"好读）。

### 12.3 怎么说

| 你说 | 效果 |
|---|---|
| `下一条` / `往下` | 光标挪一道（窗口只在光标要出屏时才滚） |
| `上一条` / `往上` | 光标回退一道 |
| `下一页` / `翻页` | 整屏往下挪 8 道 |
| `上一页` | 整屏往上挪 8 道 |
| `9` / `第 9 道` / 菜名 | 直接选中（编号是绝对编号，跟窗口位置无关，会自动滚到它） |
| 眼镜确认键 | 就做光标这道；返回键 = 光标上移一条（不摘手套也能滚） |

到顶/到底会明确回一句「已经是第一道了 / 最后一道了」，不会静默无反应。

### 12.4 可核对证据

```
COOK_SCROLL cursor=8 step=1 top=1        ← 光标到第 9 道，窗口首行滚到第 2 道
COOK_SCROLL end top=1                    ← 220ms 过渡结束，停在这个位置
COOK_PAINT mode=menu progress="菜单 · 共 11 道 · 第 1-8 道 · v66"
           timer="当前 9. 蒜蓉西兰花 · 约 8 分"
```

`node tools/test-menu-list.js`：118 项（新增滚动窗口夹紧、窗口范围、`menuTopFor` 五种落点、滚动词识别、时间格式化、列表不压麦克风行）。`node tools/mock-boot.js` 新增「滚动菜单」组：时间备注在屏、`下一条` 挪一格、窗口跟滚到 `top=1`、`下一页` 整屏、到头停住、回顶复位。

## 13.（历史）v67 新增：字号舒适档 + 墨色阶梯（重要程度用深浅表示）

### 13.1 为什么改这个

眼镜是**贴在眼前的黑底自发光屏**，但做饭的人离灶台半米、手上全是油 —— 他不能凑近，也不能腾出手去设置里翻字号。原来的问题很具体，不是审美：

1. **最小的字只有 12 号**（麦克风行 / 底栏 / 输入通道）。黑底上 12 号绿字在厨房灯光环境里要"眯一下"才看得清；
2. **次要文字的对比度不达标**：底栏 `0,110,0` 在黑底上只有 **3.2:1**（WCAG AA 正文要 4.5:1），锅里冒热气时基本等于没有；
3. **重要程度只靠色相区分**（绿/黄/青混用），亮度没有秩序 —— 主步骤和底栏的"抢眼程度"拉不开，眼睛不知道该先看哪一行。

所以这一版做两件事：**把字号排成阶梯**（越大越重要），**用同一色相的不同深浅表达重要程度**（色相只负责"是什么"）。两条都做成"只有一处总控"，改一个数字全屏跟着走。

### 13.2 字号阶梯（`const FONT`）

| 行 | 位置 / 框高 | 字号 | 内容 |
|---|---|---|---|
| `main` | `y=120`，常规 200 高 | **30** | 当前步骤（跟做页唯一主角） |
| `timer` | `y=64`，34 高 | **21** | 倒计时 / 临时提示 |
| `row` | `y=160` 起，行距 30 | **20** | 菜名 |
| `sub` | `y=330`，60 高 | **17** | 对话答案 / 副标题 |
| `said` | `y=92`，26 高 | **16** | 🗣 我说的那句话 |
| `time` | `x=480~616` | **16** | 菜单右侧「约 N 分」 |
| `progress` | `y=26`，30 高 | **15** | 第几步 / 还剩多久 |
| `meta` | `y=4 / 404 / 448` | **14** | 状态徽章 / 输入通道 / 麦克风行 / 底栏 |

- **硬下限 `FS_FLOOR = 13`**：`FONT_SCALE` 调到 0.9 也不会掉到 13 以下，杜绝"再小的字"；
- 每行的控件高度都 ≥ 字号 × 1.34（`node tools/test-ink.js` 逐行核对），所以放大不会裁字、不会压行；
- 字幕行宽度 360→420（长句少截一行）：`y=92` 位置不动 —— 字形高 21，上不碰黄字行字形（到 95）、下不碰菜单标题区（120 起）；
- 菜名列宽 468→452、时间列 500→616 加宽到 136：16 号字放得下最长的「约 1.5 时」。

### 13.3 墨色阶梯（`const INK` / `ink()`）

同一屏固定五档相对亮度，**括号里是黑底对比度**（WCAG 口径，`contrastOn()` 算，测试逐个断言 ≥ 4.5:1）：

| 档 | 目标亮度 | 黑底对比度 | 用在哪 |
|---|---|---|---|
| `key` | 0.62 | 13.3:1 | 只闪一下：刚选中的菜、「显示重点」的当前步、收工总页标题 |
| `main` | 0.50 | 11.0:1 | 当前步骤、光标停的那道菜、菜单标题 |
| `sub` | 0.36 | 8.2:1 | 对话答案、倒计时、副标题、临时提示 |
| `aux` | 0.26 | 6.2:1 | 第几步/还剩多久、时间列、状态徽章 |
| `meta` | 0.18 | **4.5:1** | 麦克风行、底栏、输入通道（最低一档，仍过 AA） |

`ink(rgb, 档位)` 的做法：保持色相等比缩放 RGB，落到目标亮度；**红/蓝这类天生到不了 0.5 的色相取"最亮的可达值"**（宁可红字略暗，也不把它洗成粉色 —— 洗成粉色就不像"异常"了）。结果带缓存，每帧几十次调用也只是查表。

于是分工清楚了：

- **色相 = 是什么**：绿=正常步骤、黄=计时、青=答案/处理中、橙=提醒、红=异常；
- **深浅 = 有多重要**：主步骤 11:1 一眼就抓住，底栏 4.5:1 余光可见但不抢戏。

顺带修掉两处"看不见"：忌口菜原来压到 `0,110,50`（3.2:1），现在压到 `meta` 档并靠「（辣）」标记；时间列同理。

### 13.4 怎么说

| 你说 | 效果 |
|---|---|
| `看不清` / `字太小` / `舒适` | 舒适档：15 号及以下的小字整体 +2（14→16、15→17），主步骤/菜名不动 |
| `字小一点` / `常规字号` / `字太大了` | 回到常规档 |
| `大字` | 只放大主步骤 30→38（沿用 v63 的布局指令） |
| 已经是该档再说一遍 | 明确回「已经是舒适字号了 · 嫌小再说「大字」」，不假装执行 |

舒适档**只抬 15 号及以下那几档**，因为那才是真正看不清的行；菜名(20)、主步骤(30) 再放大就会压行 —— 那是「大字」布局的活。两条指令分工写在 `COMFORT_MAX_BASE` 这一个常量上。

### 13.5 可核对证据

```
COOK_FONT boost=2 meta=16 progress=17 row=20 main=30   ← 小字抬了，菜名/主步骤没动
COOK_FONT_CMD comfort changed=true boost=2 meta=16 progress=17
COOK_FONT_CMD comfort changed=false boost=2 ...        ← 第二遍明确说"已经是了"
COOK_FONT boost=0 meta=14 progress=15 row=20 main=30   ← 「字小一点」还原
```

`node tools/test-ink.js`：**187 项**（字号阶梯顺序、最小字号 ≥14、11 行的框高装得下字号、舒适档只抬小字、五档亮度严格递减、7 个语义色 × 5 档 = 35 组对比度 ≥ 4.5:1、`ink` 幂等、纯黑/纯白边界、源码里不许再有手写字号/手写文字颜色、**词面反例「火太小了 / 火大一点 / 再放大蒜 / 盐太少了」不许被当成调字号**）。`node tools/mock-boot.js` 的「布局指令」组新增 4 条：`看不清` → `COOK_FONT boost=2` 且菜名列仍是 20 号、连说两遍报「已经是了」、`字小一点` → 14/15 回来、「火太小了」不被当成调字号。

## 14.（历史 · 本版已移除）v68 新增：忌口 / 喜好的记忆

### 14.1 为什么要有它

做饭的人最常说的两句话是「我不吃辣」和「我吃什么都行」——但这两句**都不该每次重新说一遍**。
之前只有一个 `noSpicy` 开关：说完「不吃辣」只影响这一次菜单，重启就忘了；而且只认「辣」这一种。

这一版把它做成"能记一辈子的三句话"，但仍然守住一条线：**只提示，不阻止**。
决定权在用户手里，机器只是"记得他说过"，并且在他要选那道菜时把话递到眼前。

### 14.2 它就三件事

| 你说 | 发生什么 |
|---|---|
| `我不吃香菜` / `我对花生过敏` / `我不喜欢吃葱和姜` / `我讨厌香菜` | 记下来（最多 8 样），存进 `taste.json`；菜单里含它的菜名后标 `（含香菜）` |
| `我爱吃辣` / `我喜欢吃折耳根` / `多放点蒜` | 记成"喜好"；说「推荐」时先推含它的菜 |
| `我有什么忌口` | 回一句「🧠 我记得：不吃香菜 · 爱吃辣」 |
| `忘掉香菜` / `清空忌口` | 删掉，菜单后缀立刻撤干净 |

- **说一遍就够，跨开机**：存在应用数据目录 `taste.json`（和 `custom-dishes.json` 同级，包外、不进仓库）；
- **只认食材，不瞎猜**：词表收了 100+ 常见食材（香菜 / 葱 / 姜 / 蒜 / 辣 / 花生 / 虾 / 鸡蛋 / 牛羊肉…，含折耳根、香椿、秋葵）；不认识的明说「这句我没听出是什么食材」，绝不把「火候」记成忌口；
- **说「不吃辣」= 同时打开辣味筛选**：和 v66 那个开关是同一套状态，不另造一套逻辑。

### 14.3 提示放在哪（"对应的地方"）

| 位置 | 提示 | 为什么放这 |
|---|---|---|
| 菜单菜名 | `3. 蛋炒饭（含葱）` | 选之前就能看见；后缀先留位再截菜名，长菜名也不会把 `（含葱）` 截掉 |
| 菜单第一次进 | `🧠 我记着：不吃葱 · 含它的菜名后标「（含X）」` | 只在每次开机第一次进菜单说一遍，之后靠后缀自解释，不常驻占底栏 |
| 跟做页 | 底栏 `⚠ 这步有葱（你忌口）· 不想放就说「跳过」` | 只在**这一步**真的用到时才提醒（第 1-3 步不打扰），16 秒后自己退场 |
| 推荐 | `推荐 蛋炒饭 · 约 10 分 · 你爱吃辣` | 忌口菜直接不推；全都含就说清楚"实在没有全避开的" |
| 生成菜谱 | 模型提示词里加一句 `用户忌口：香菜` | 生成时就不放，比生成完再标更省事 |

### 14.4 词面必须窄（这是老坑）

`不吃` 才算忌口；`不放盐` / `别放葱` / `少放点辣` 是**这一锅的做法**，一个字都不记。
`test-taste.js` 里有 28 条反例盯着这件事——包括 v63 栽过的 `火大一点`、`再放大蒜`，以及 `我不吃这个`、`我不吃亏`、`可以吃了`。

### 14.5 可核对证据

```
COOK_TASTE load "不吃葱"
COOK_TASTE add kind=avoid added=["葱"] removed=[] existed=[] saved=true all="不吃葱"
COOK_TASTE step=4 hit=葱
COOK_TASTE remove kind=any added=[] removed=["葱"] existed=[] saved=true all=""
COOK_TASTE list "不吃葱"
```

`node tools/test-taste.js`：**80 项**（14 条正例 / 28 条反例 / 互斥 / 上限 8 / 缓存不被写坏 / 菜谱命中与后缀格式 / 存储不抛错 / 源码接线必须排在菜单与收尾之前）。
`node tools/mock-boot.js` 新增「忌口记忆」组：说「我不吃葱」→ 菜单里出现 `（含葱）` → 第 1-3 步不打扰、第 4 步底栏提醒 → 「忘掉葱」后后缀撤干净。
